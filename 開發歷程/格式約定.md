# SkinDetect 格式約定 v1

本檔定義專案內所有索引檔、紀錄檔與實驗 README 的共同格式。目的不是美觀，而是讓**同一件事在不同檔案裡有同一個名字**，使跨檔比對與漂移偵測成為可能。

適用範圍：`開發歷程/`、`檔案室/`、`實驗紀錄庫/`、`模型資產庫/`，以及各實驗資料夾的 `README.md` 與 `result.json`。

## 一、單一權威原則

每一類資訊只有一個權威來源，其他檔案指向它，不複製：

| 資訊 | 權威來源 | 其他檔案的作法 |
|---|---|---|
| **事件時間軸** | `開發歷程/時間軸.md`（由 `build_timeline.py` 產生） | 連結過去，不自建時間表 |
| **匯總節點與修正** | `開發歷程/checkpoints.json` | 連結過去 |
| **圖表與配套檔案逐檔索引** | `檔案室/圖表資料庫/總索引.csv` | 連結過去 |
| **UI 實驗檔案索引** | `實驗紀錄庫/registry.json` | 由 `sync_registry.py` 產生，不手改 |
| **UI 可推論模型清單** | `模型資產庫/model_registry.json` | 由 `sync_models.py` 產生，不手改 |
| **資料切分與標籤** | `資料治理與泛化修復/data/unified_manifest_v1.csv` | 正式訓練唯一輸入 |

`檔案室/圖表資料庫/README.md` 的日期表是**圖表歸檔清單**，不是專案時間軸；兩者用途不同，前者只列有歸檔產物的任務。

## 二、受控詞彙

以下詞彙表由 `開發歷程/build_timeline.py` 的 `STAGES` 與 `STATUSES` 定義，為唯一版本。

### 階段（stage）

| 代碼 | 名稱 |
|---|---|
| `DATA` | 資料建置階段 |
| `VAL` | 驗證階段 |
| `S1` | 第一階段 |
| `S2` | 第二階段 |
| `S3` | 第三階段 |
| `SITE` | 部位預測階段 |
| `MIX` | 多來源訓練階段 |
| `GOV` | 泛化修復階段 |
| `SCR` | 基底篩選階段 |
| `BASE` | 基底模型階段 |
| `CUR` | 課程學習階段 |
| `META` | 專案治理 |

**已知的既有不一致**（`check_consistency.py` 會列出，暫以對照表相容，不強制改寫既有檔案）：

| 權威名稱 | `檔案室` 舊值 | `實驗紀錄庫` 舊值 | `模型資產庫` 舊值 |
|---|---|---|---|
| 泛化修復階段 | 泛化修復階段 | 泛化修復 | 資料治理後模型 |
| 基底篩選階段 | 基底篩選階段 | 基底篩選 | — |
| 基底模型階段 | 基底模型階段 | 基底模型 | — |
| 多來源訓練階段 | 多來源訓練 | 多來源訓練 | 多來源訓練 |

`模型資產庫` 的 `group` 另含方法別分類（`並行特徵`、`凍結 Backbone`、`完整微調`），**那不是階段**，應改用獨立欄位 `method_group` 表示。

### 狀態（status）

`已完成`、`進行中`、`未開始`、`已結案`、`已鎖定`、`已停用`

- `已結案` 專指**負面結果且正式停止投入**，與 `已完成` 區分。
- `已鎖定` 指前置條件未達成而暫停（例：第三階段 v10 等待 v9 三 seed）。

## 三、資料格式規則

1. **日期**一律 `YYYY-MM-DD`；**時間戳**一律 ISO 8601 含時區，例 `2026-09-08T11:10:20+00:00`。
2. **指標**在機器可讀檔（`*.json`、`*.csv`）一律存 0–1 的 float；在人類可讀文件（`*.md`）一律寫百分比並保留兩位小數。**不得**在 JSON 裡存 `"72.06%"` 這種字串。
3. **seeds** 一律為整數陣列 `[17, 42, 2026]`；另可有 `seed_count`。單 seed 結果必須同時帶 `"pilot": true`。
4. **路徑**一律為專案根目錄的相對路徑，使用正斜線。
5. **識別碼**（`id`）一律小寫 snake_case ASCII；中文名稱放 `name_zh`。
6. 每個機器可讀索引檔的頂層必須有 `schema_version`、`generated_at`、`generator`。`schema_version` 統一命名空間 `skindetect-index-v1`。
7. 由腳本產生的檔案，第一行或頂層必須聲明「請勿手動編輯」與產生器路徑。

## 四、實驗 README 的標準狀態區

每個實驗資料夾的 `README.md`，在一級標題之後、原有內文之前，插入一段固定欄位的狀態區。**原有內文完全不動** —— 狀態區只是加上可機器解析的頭部。

```markdown
# <原標題>

<!-- skindetect:status v1 -->
| 欄位 | 值 |
|---|---|
| 階段 | 泛化修復階段 |
| 首次執行 | 2026-09-06 |
| 狀態 | 已完成 |
| seeds | 17／42 |
| 主要指標 | 三來源平均 BA 72.06%（seed 17） |
| 正式輸入 | `資料治理與泛化修復/data/unified_manifest_v1.csv` |
| 結果證據 | `資料治理與泛化修復/results/formal_v1/regularized_seed17/result.json` |
| 歸檔 | `檔案室` 任務 10 |
| 時間軸 | [`開發歷程/時間軸.md`](../開發歷程/時間軸.md) |
<!-- /skindetect:status -->

<原有內文，一字不動>
```

`<!-- skindetect:status v1 -->` 註解標記讓工具能安全地重新產生此區塊而不觸及內文。

## 五、匯總節點與計畫文件

- **匯總節點**（`節點NN_*.md`）為凍結快照：原文不得改寫，更正一律追加在「後續修正」區，並註明日期、原因、證據路徑與 `original_text_modified: false`。
- **計畫文件**（`CP-NNN_執行計畫_*.md`）為活文件：可修改，但每次修改須在末節「修訂紀錄」留一列。版本號撞號時以時間先後為準，後者改號並註明原因。
- 兩者的機器可讀對應物為 `checkpoints.json`，其 `corrections` 陣列與節點的「後續修正」區逐筆對應。

## 六、證據鏈規則

沿用 `開發歷程/README.md` 節點規則第 4 條，並補強：

- 任何寫進節點或計畫的數值，必須能連回 `.json`、`.csv`、checkpoint 或驗證報告。
- 若某數值目前只存在於 Markdown 而無機器可讀來源，**必須明確標註**（現存案例：`noisefilter_清單檢查報告.md` 的 delta cosine 0.9953，見 `節點01` 後續修正 01）。
- 引用路徑必須是該數值**實際所在**的檔案，不得指向同主題但不含該欄位的檔案。

## 七、一致性檢查

```powershell
python "開發歷程/check_consistency.py"
```

檢查項目：時間軸與各索引的階段詞彙是否可對應、`generated_at` 是否過期、被時間軸標為未歸檔的事件是否確實不在 `檔案室`、節點的「後續修正」筆數是否與 `checkpoints.json` 的 `corrections` 一致、實驗 README 是否具備狀態區。

輸出為報告，不自動修改任何檔案。
