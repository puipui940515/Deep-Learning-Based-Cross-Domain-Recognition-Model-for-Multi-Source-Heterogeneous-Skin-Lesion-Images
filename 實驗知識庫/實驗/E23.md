# E23　class_floor：給 SCC 一道類別抽樣質量保底（R2-SCC）

- 日期：2026-11-02（～2026-11-06，重跑與作廢）
- 狀態：作廢（R2-SCC 兩次啟動都沒跑完、沒有 result.json；續跑因程式碼雜湊變更而永久失效）
- 相關：前置 ADR-0002（取樣器缺陷）、ADR-0006 線索一、E20、E22；同日被 E24–E26 的證據質疑；E36 時段（archive SD-009）建議不要重跑

## 目的
ADR-0002 記錄的取樣規則是「每個來源質量相等（各 1/4）＋來源內各類等質量」，所以只存在於單一來源的類別會被結構性卡住。SCC 只出現在 ISIC_Archive_Expanded：

| 類別 | 張數 | 來源數 | e=1.0 抽取佔比 |
|---|---|---|---|
| SCC | 1,687 | 1（只有 ISIC） | 3.12% |
| DF | 489 | 3 | 10.27% |
| VASC | 377 | 3 | 10.27% |

DF、VASC 張數不到 SCC 的三分之一，抽取次數卻是三倍多；而 SCC 在 R2 的 val_assess recall 是 0.562，八類倒數第二。這是 ADR-0006 三條線索裡最便宜的一條：不動 manifest、一個開關、一次訓練。

## 做法
- 在 `scripts/train.py` 取樣器加 opt-in 的 `class_floor`：質量低於 floor 的類別拉到 floor（保留原本的來源組成），其餘類別等比例縮小；floor 太高會 assert 失敗。
- 用 `audit/e23_class_floor_verify.py` 驗證未啟用時行為不變：把舊公式與新公式各寫一次，餵同一份 manifest，逐格比對浮點數是否完全相等。
- 設 `class_floor = 0.10`：剛好低於 DF／VASC 的 10.27%，所以只拉 SCC。
- 新增 run `R2-SCC` = R2 + `class_floor 0.10`，其餘不動（刻意不加 R2-REG 的 mixup／erasing），20 epoch，seed 17。
- 事先寫下失敗條件：SCC recall 的 Wilson 區間與 R2 重疊 → 取樣不是瓶頸；SCC recall 升但選定指標降 → 來源不平衡代價大於收益；全部在種子噪音（1.68–3.69pp）內 → 什麼都沒證明。

## 結果
未啟用時的等價性驗證（e=0.5 與 e=1.0，class_floor 為 0 或 None）：64,780 個權重逐位元完全相等，通過。

`class_floor = 0.10` 的期望抽樣分布（不是實際計數）：

| 類別 | 現在 | 加保底後 | 每張重複次數 |
|---|---|---|---|
| SCC | 3.12% | 10.00% | 1.200 → 3.841（3.2 倍） |
| AKIEC／BCC／BKL／NV／MEL | 15.27% | 14.18% | 各降約 1.08pp |
| DF／VASC | 10.27% | 9.54% | 各降 0.73pp |

代價：來源質量不再各 25%，ISIC_Archive_Expanded 25.00% → 30.32%，其餘三個來源各 23.23%。

run 的實際狀況：

| run | 經過 | 結果 |
|---|---|---|
| `R2-SCC_90a7248f_seed17`（11-02 啟動） | 助理以為已停掉，實際子程序仍在跑並與 E28 搶 GPU 約 34 分鐘；停在 epoch 4/20 | 無 result.json。val_select 最差來源 0.5250 → 0.5546 → 0.6076 → 0.6170 |
| `R2-SCC_33a22e42_seed17`（11-05 以新身分重跑） | 舊 run 的 --resume 被身分閘門擋下（code_sha256 已變），改以新身分從頭跑；中途暫停、續跑，11-06 停在 epoch 13 | 無 result.json。epoch 13 val_select 最差來源 0.6546（ISIC，每個 epoch 都是 ISIC），mean_source 0.7412 |

`R2-SCC_33a22e42` epoch 13 在 val_select 的逐來源 macroF1_ge30：BCN20000 0.6762、HAM10000 0.8218、ISIC_Archive_Expanded 0.6546、PAD-UFES-20 0.8120。停止時仍在改善（patience 0）。

## 推論
- 當時的判斷：這個開關是拿「來源等質量」換「類別不被結構性餓死」，兩者無法同時成立；選定指標會懲罰來源不平衡，所以可能反而變差，那正是要測的。
- 同日 E24–E26 給出三條獨立證據指向「拉高 SCC 抽樣是錯方向」（SCC precision 0.483 已低於 recall、τ 掃描推高 recall 時 precision 掉到 0.415、貪婪偏置搜尋自己選擇不動 SCC），助理事先預測 R2-SCC 的 SCC recall 會升、precision 會降、F1 不會顯著改善。助理一度決定讓它跑完（取樣改變的是模型學到什麼，與決策邊界是不同機制），之後為了讓出 GPU 給 E28 而停掉。
- 後來 E36 時段建檔（archive SD-009）時指出：SCC 只存在於四個來源中的一個（ISIC_Archive_Expanded 2,197 張，其餘各 0 張），多抽同一來源的同一批圖不會產生跨來源訊號，而選定指標取的是最差來源，所以建議不要重跑 R2-SCC，除非先解決來源問題。
- 2026-11-06 使用者核准修改 `train.py`（細分類訓練），R2-SCC epoch 13 的續跑就此作廢；之後 manifest 也在 11-07 變更，這個 last.pt 永遠無法續跑。線索一在後來的盤點裡被列為「啟動過但沒跑完」。

## 限制
- 只有一顆種子（seed 17），R2 系列沒有同結構的噪音基線（E21 的 A9）。
- 只試一個 floor 值（0.10），沒有掃描。
- 抽樣分布表是期望值，不是實際計數。
- epoch 13 的數字是訓練中途在 val_select 上的值（整理者註：不能和 R2 在 val_assess 的 0.6541 直接比）。
- 改動不改變訓練資料內容、只改變看的頻率，所以不影響 E17／E18 的「模型端介入上限 10.39pp」。
