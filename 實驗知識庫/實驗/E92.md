# E92　run 身分（run_id）解析的獨立複製品：證明改 train.py 沒有改變預設行為

- 日期：2026-11-08（2026-11-09 加 KAN head 時再次使用）
- 狀態：完成（驗證工具，之後每次改 train.py 都沿用）
- 相關：前置 E90（manifest 變動使 run_id 失效）、R2-REG-XLONG 停跑；後續 R2-REG-RESTART（`--init-from`）、R2-KAN（head='kan'）、E93

## 目的
2026-11-08 使用者改方案，要從 R2-REG-LONG 的最佳權重接續訓練，需要替 train.py 新增 `--init-from` 旗標。CONTEXT.md 第 8 節要求改 src/ 或 scripts/ 必須「程式化驗證預設行為完全相同」。但 train.py 把自己的原始碼雜湊進 `cfg['code_sha256']`，而它又在 identity_cfg 裡，所以**任何**對 train.py 的修改都會讓全部 run_id 改變，「run_id 不變」不可能當驗證條件。真正該驗證的是：**identity_cfg 除了 code_sha256 之外完全沒變**。

## 做法
- 新寫 `audit/e92_identity_replica.py`：獨立複製 train.py 中 cfg 解析與 digest 計算的那一段，**完全不含 init_from 的邏輯**。
- 放在 audit/，不在 code_paths 內（腳本內 assert 驗證），所以新增它本身不改變 code_sha256。
- 第一步（改 train.py 之前）：確認複製品能逐一重現 `train.py --check-only` 印出的每個 run_id，證明複製正確。
- 第二步（改 train.py 之後）：複製品會自動抓到新的 code_sha256；若一個不知道 init_from 存在的程式仍能預測改過的 train.py 的每個 run_id，就證明 init_from 以外的 identity_cfg 一個位元都沒變。
- 再逐鍵比對全部 run 的 identity_cfg。

## 推論
- 預設行為逐位元相同，只有 code_sha256 這個記錄用的欄位改變。
- 既有 run_id 因此第三次全部失效（2026-11-06 改 models.py、2026-11-07 改 manifest、2026-11-08 改 train.py）；已完成 run 的 result.json／config_snapshot.json 一律不動（血統紀錄）。
- 2026-11-09 啟動 R2-REG-LONG 第二顆種子時，本實驗的驗證被拿來說明 seed17（code_sha256 5fd7c5d2…）與 seed42（583aa690…）的 digest 不同只是這個純記錄用欄位造成的，兩顆種子之間沒有行為差異；報告寫兩顆種子的結果時必須附上這一段。
