# E52　用本機 Codex 標八張病灶框，和偵測器的框比對

- 日期：2026-11-04
- 狀態：完成（結論：Codex 品質不如偵測器，只適合當驗證用的第二意見，不拿來產生標註）
- 相關：前置 E8（偵測框審查）；後續 E53（用 Codex 交叉驗證 BCN／PAD 的偵測框）、E55 引用其結論

## 目的
使用者排程要「讓 GPT 標病灶位置」。瀏覽器裡的 ChatGPT 未登入、無法附檔，助理不登入帳號，所以改用本機安裝的 Codex CLI。這次是小規模試用：Codex 看圖給出的病灶框，和現有偵測器（`bbox_detect.json`）的框一致到什麼程度。

## 做法
- 影像：`data/annot_seed/` 八張，每類一張，取自 train split（seed 20261104）。
- Codex 以 read-only sandbox 執行，只看影像、不讀寫檔，回傳每張病灶的正規化 xywh。
- 與偵測器的框算 IoU。
- 模型：這次**沒有指定 -m**，因此用到 config.toml 的預設 gpt-6-astra＋high；使用者規定的預設是 gpt-6.1-sol／medium，之後每次都顯式指定。
- 執行時踩到的坑：`-i/--image` 是可變長參數，prompt 放最後會被當成一張圖吃掉，改由 stdin 送 prompt。

- 對照圖：`E52_Codex框對照.png`。

## 推論
- 在病灶瀰漫的影像上，Codex 會把整張畫面框起來（DF 那張 IoU 0.393）。E53 的腳本說明據此判定：Codex 的品質不如現有偵測器（偵測器對遮罩真值的 box IoU 為 0.9064），所以它的角色是**驗證**，不是**標註**。
- E55 引用時稱「E52 量過 Codex 是比較弱的標註者」。
- 流程面的結論：之後每次呼叫 Codex 都顯式指定模型（gpt-6.1-sol／medium）。

## 限制
- 只有 8 張（每類一張），沒有區間估計。
- 對照的是偵測器的框，不是人工真值。
- 模型用錯（吃到預設的 gpt-6-astra／high），不是之後規定的設定。
