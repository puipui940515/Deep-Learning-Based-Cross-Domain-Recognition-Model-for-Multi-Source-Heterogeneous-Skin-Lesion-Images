# E79　通用的訓練進度曲線與停滯判斷工具（套用於 R2-SWIN、R2-SWIN224、R2-REG-LONG、XLONG、RESTART）

- 日期：2026-11-06（～2026-11-12）
- 狀態：完成（工具；基準線 2026-11-12 同步更新）
- 相關：由 E73 通用化而來；被用於 E81／E83（R2-SWIN）、E89（R2-SWIN224）、E91（R2-REG-LONG）等；桌面檢視器 watch_training.py 共用同一套判準與基準線

## 目的
E73 寫死 R2-FINE 與 R2；E79 改成吃 `--run` 與任意多個 `--ref`，之後每個 run 都用同一支看進度。分開回答兩個問題：

1. 離目標多遠：目標取自檔案裡已有的基準線（同族對照 run 的 val_select 最佳分、全專題最高分），加上種子噪音帶 1.68–3.69pp（E18／E21）——差距沒超出這個帶就不能宣稱贏，所以目標是一條帶，不是一條線。D2 的「每類召回 0.85」不畫（已否決，且是召回不是 macro-F1）；val_assess 數字也不畫。
2. 有沒有停滯：最後 k 個 epoch 的 OLS 斜率與 95% 區間（區間不含 0 才算還在進步）、距最佳幾個 epoch、對照 run 同 epoch 之後還賺多少、對照 run 最長連續沒進步段。n < 3 時直接說「無解析度」。

## 做法
- 只讀 results/ 下的 progress.json 與 result.json，不碰 GPU、不中斷訓練、不讀 val_assess。
- 每次輸出一張四面板進度曲線圖與一份停滯判斷 JSON（以 run 名稱命名，重跑會覆寫同名檔）。
- 基準線放在 `E79_基準線.json`，只放 val_select。

## 結果

|---|---|---|---|---|

R2-REG-LONG 途中的查核（2026-11-07 21:47，ep34）曾判「以 10 個 epoch 尺度看還在進步」（+0.200 pp/ep，CI [+0.069, +0.331]）；2026-11-08 02:27（ep48）時所有斜率區間都含 0，但同段出現 ep41／42／47 三次新高，紀錄解讀為「緩慢上移的水準上大幅震盪」、是解析度不足而非平台。

## 推論
- R2-SWIN：用完 20 epoch 的預算停下，不是收斂停下（斜率仍正但區間含 0、train_loss 仍確定下降）。
- R2-REG-LONG 跑完時判定「是真的跑到停了才結束」（ep50 之後 lr < 7.6e-06）。
- 2026-11-12 同步：基準線 JSON 三條數值不改，只把標籤改為「舊 manifest」並移除已不成立的「全專題 val_select 最高」（R2-REG-LONG 在現行 manifest 的 val_select 是 0.6939）；檢視器的預設對照改為現行 manifest 的 R2-REG-LONG 與 R2-REG-RESTART。
- 另修過一個 bug：supported_labels_ge30 是類別索引清單不是數量，直接進格式字串會 TypeError，改成取 len。

## 限制
- k 的選擇影響判斷：k=5 解析度太低；60 epoch 以 k=10、120 epoch 以 k=20（事先登記）。
- 斜率判斷與學習率退火糾纏：餘弦排程 T_max 綁在 epochs 上，末段「變平」有一部分只是 lr 降到接近 0（見 R2-REG-LONG 相關紀錄）。
- 早期 R2-SWIN、R2-SWIN224 的判斷 JSON 中「全專題 val_select 最高」的目標標籤已過時。
