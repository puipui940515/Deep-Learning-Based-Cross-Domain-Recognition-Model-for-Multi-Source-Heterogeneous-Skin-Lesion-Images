# E111　run 索引：把 results/ 底下所有 run 正規化成一張表

- 日期：2026-11-09
- 狀態：完成（衍生產物，可刪除重建）
- 相關：同類的實驗目錄見 E118；E117 缺陷 A4（兩代 manifest 混用）出自此表

## 目的
使用者問要不要做資料庫存實驗數據。助理先量現況：47 個 run 目錄（38 個有 result.json）、reports 255 個檔、audit 腳本 127 支、ADR 7 份、Day 紀錄 8,043 行；result.json 有兩代不相容的 schema。當天寫 survey 腳本只找新格式的路徑，結果默默漏掉大部分 run。結論是**不做資料庫，做一個可重建的索引**：
1. 真正的問題是兩代 schema，資料庫不會幫忙和解，正規化器才是全部的工作量；
2. 本專題的完整性模型是「內容雜湊 + result.json 不可覆寫」，資料庫會變成第二個真相所在地並漂移，可重建的索引不會；
3. 38 個 run 是試算表的規模；
4. 離截止很近。

使用者回覆「做索引」後實作。

## 做法
- 腳本走訪 `results/*/result.json`，兩代格式都認；沒有 result.json 的目錄標為 incomplete，也要列出。
- 主指標 worst_source_macro_f1_ge30 依序從四條路徑取得：現行格式 `metrics.val_assess.*` → 舊扁平格式 `val_assess.*` → 由分來源 macro_f1_ge30 取最小（兩種格式各一）；都拿不到就寫明原因，絕不默默跳過。
- 輸出 `reports/run_index.csv`（utf-8-sig，Excel 可直接開）與 `run_index.json`；欄位含狀態、schema、主指標與其來源、best_epoch、骨幹、尺寸、head、crop、held_out、取樣與增強參數、seed、manifest_sha256、code_sha256 等。
- 排行榜依 manifest 分組印出，並標出哪一組是現行的。

## 結果
- 47 個 run 目錄：complete 38、incomplete 9、unreadable 0；schema：v1 26、legacy_flat 12。
- 主指標拿得到 38／47：重算（min over val_assess logits）15、舊扁平格式 12、現行格式 11。拿不到的 9 個全部是 incomplete，逐一列名。
- 只有 4 個 run 綁現行 manifest（29d29514），其餘 34 個綁舊的（462a5df9）；兩者的 val_assess 不是同一組影像（9,588 vs 9,652 筆），跨組比高低無效。

## 推論
做索引當場修正助理自己三個錯誤：
1. 先前說「主指標只出現在 11/38」是量錯路徑——舊格式放在 `val_assess.*`，12 個舊 run 其實都有。
2. 先前說「11 個已完成 run，全距 3.7pp」漏掉 27 個且沒告知使用者；正確是 38 個。
3. 先前一直說「G-DET 擋住 R2-DET」，但其實 R2-DET 有一個 rerun 已跑完（crop=detect、ep19、0.6777，舊 manifest 組第一）；它與 R2-REG-LONG 的 0.6819 不在同一個評估集上，不能排名次。

新發現（需在同一 manifest 上確認）：R0S-P（224、spatial head）0.6709、R0S 0.6611；先前說「spatial head 沒有贏過 gap」引的是讀出集中度（A2），不是分數，分數上 spatial head 並沒有被比下去。

後來 E117 據此列出缺陷 A4：ADR-0007 的集成 +3.49pp 是在舊 manifest 上量的。
