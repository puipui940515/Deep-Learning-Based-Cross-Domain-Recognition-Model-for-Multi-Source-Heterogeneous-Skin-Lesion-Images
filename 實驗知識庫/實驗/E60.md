# E60　偵測裁切三方對照：不裁 vs k=1.5 vs k=1.0

- 日期：2026-11-05
- 狀態：完成（偵測裁切不採用：排除「介入太弱」的但書）
- 相關：前置 E54、E55（k=1.0 的幾何依據）、E56（k=1.5 對不裁）；同步 E59b；後續 E65（PAD 退步仍未解釋）

## 目的
E56 量到 k=1.5 的偵測裁切沒有可證明的效果，但留了但書：k=1.5 下全體 37.7% 的影像 zoom ≤ 1，等於沒裁，所以「沒效果」可能只是「介入太弱」。k=1.0 是 E55 算出的最強且不損失病灶的設定（裁切方形完整包住偵測框、四個來源的 zoom 全部翻倍以上）。這可以直接檢定：
- 若「介入太弱」是對的 → k=1.0 應明顯好過 k=1.5；
- 若 k=1.0 沒有比較好 → 介入強度不是原因，偵測裁切就是沒用。

## 做法
- 使用者指定把 config.json 的 `runs['R2-DET']['k']` 從 1.5 改為 1.0（只改這一行），新 run `R2-DET_c00c24e5_seed17`；2026-11-05 04:19 → 13:32 跑完（中間 GPU 被其他程式佔用而變慢），best_epoch 19。
- 三個 arm：不裁 `R2_0edf1ecc_seed17`、k=1.5 `R2-DET_e26673e6_seed17_rerun1`、k=1.0 `R2-DET_c00c24e5_seed17`；骨幹、解析度、取樣、預算、選檢查點規則全部相同，只有裁切不同。
- 分層配對 bootstrap 2000 次（來源內重抽、共用重抽）。val_assess 讀 1 次。

## 推論
- **E56 留的但書排除掉了。** zoom 翻倍、一個像素的病灶都沒切到，成績在兩個切分都沒有變好。所以「偵測裁切沒效果」不是因為 k=1.5 介入太弱，**就是沒用**。
- PAD 隨 k 變小而持續惡化；同日 E59b 再次排除墨圈解釋，PAD 退步原因仍未解釋。
- 2026-11-16 紀錄：crop=detect 的 G-DET 核准綁在舊 manifest，在現行 manifest 上被擋住，要用須由人重新核准；引用的成效數字即本頁 val_select 結果。

## 限制
- 單一 seed（17），差值都在種子噪音帶（1.68–3.69pp）附近、CI 全部含 0。
- 使用舊 manifest。
- 2026-11-09 的一份 run 清單把 k=1.0 這個 run（val_assess 0.6589）標成「R2-DET(舊)」，實際上它是較新的 k=1.0 run（整理者註，見回報的矛盾清單）。
