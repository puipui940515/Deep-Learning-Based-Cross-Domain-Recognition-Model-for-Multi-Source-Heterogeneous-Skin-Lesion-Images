# E22　系統清冊：results/ 底下每個 run 的身分、狀態與指標

- 日期：2026-11-02（12:40 初版）～2026-11-04（第 9 節增補）；實驗索引記為 2026-11-04
- 狀態：完成（基礎設施盤點）；第 2 節的三個孤兒同日由使用者指示刪除；第 9 節增補 SHARED_* 與前處理分群
- 相關：E16（預算截斷判準）；E22b（腳本改動的等價性驗證）；E45（未提交的 draft 前處理）；ADR 0001、0003、0004

## 目的

`results/` 累積了 21 個資料夾（8.2 GB），其中有同一 run 名稱配不同 digest 的孤兒、沒有 result.json 的半成品、以及依賴已否決閘門的設定，光看資料夾名稱分不出哪些還算數。這份清冊把它攤開。

## 做法

- `audit/e22_registry.py`：掃 `results/`、`config.json` 與 `reports/*.json` 的閘門欄位；指標一律從每個 epoch 的混淆矩陣重算 val_select worst-source macro F1(ge30)，因為早期 result.json 沒有 ge30 欄位。
- 「預算截斷」= 最佳 epoch 就是最後一個 epoch。
- digest 定義（`scripts/train.py` 240–253 行）：`code_sha256` 是全部 src／scripts／stage2 程式碼雜湊的串接；digest = sha256（去掉 seed 的 cfg JSON ＋ git commit）前 8 碼，所以任何 commit 或程式碼改動都會讓往後的 run 拿到新 digest。
- 2026-11-04 腳本改成兩種 result.json schema 都讀（見 E22b）。

## 推論

- 資料穩定、程式碼不穩定：沒有任何一組 run 是「只有一個變因不同、程式碼完全相同」，所以跨 run 比較有一個真實但無法量化的雜訊來源；這是 ADR 0004 要靠對程式碼版本不敏感的「錯誤重疊」檢定的原因。
- R3、R4、R6 留在 config 不影響其他 run 的 digest（`cfg.pop('runs')` 在算 digest 之前），但會讓人誤以為可以跑。
- digest 只告訴你有差，不告訴你差在哪。

## 限制

- 只掃 results、config 與閘門欄位，沒有載入 best.pt 驗證權重完好。
- 「預算截斷」只看最佳 epoch 是否為最後一個；被早停攔下的 run 標「否」是另一回事。
- 指標一律重算，可能與各 run 自己的 result.json 不同（刻意，見 ADR 0001）。
- 報告第 2 節寫「沒有刪除任何東西」；同日 13:05 使用者指示刪除三個孤兒（刪前小檔存於 `reports/E22_孤兒run存查/`，results 8.2G → 7.8G）。
