- 狀態：作廢（排程以錯誤的 Python 環境啟動，一啟動就 ImportError 退出，從未產出結果；之後未再重跑）
- 相關：排在 R2-KAN（見 E108）之後、R2-REG-LONG seed 42 之前；失敗經過記於 E117（缺陷 D1）；後來 E130 另以 batch 8／16／32 實測顯存（問題不同）

## 目的
使用者問「高解析度怎麼吃得下」。助理盤點後發現 AMP 與梯度累積已經在用，唯一沒用的大槓桿是梯度檢查點（gradient checkpointing）。支持提高解析度的證據有：同骨幹 R2-SWIN224 → R2-SWIN（只差 size 與 batch）0.6446 → 0.6720，+2.74pp；E102 量到 ISIC 只保留 7.5% 像素。要知道這張卡實際能訓到多大，必須先量**訓練**時的峰值顯存。

## 做法
- 量 forward + backward + optimizer step 的峰值顯存，不是只有推論。
- 三個軸：size 384／512／640／768／896／1024 × batch 8／4／2／1 × 梯度檢查點 關／開；每個 size 由大到小找第一個不 OOM 的 batch，記峰值與達到 effective_batch 32 所需的累積步數。
- AMP 與優化器分組（parameter_groups_with_layer_decay）與 train.py 一致。
- 梯度檢查點只在探測腳本內以 torch.utils.checkpoint 包住 model.features 的每個 stage，train.py 沒有改；量完再決定要不要進 train.py。
- 安全檢查：若偵測到有 train.py 在跑就中止（否則量到的是殘餘顯存）。這個檢查曾實測有效（R2-KAN 在跑時直接退出，退出碼 1）。
- 排程：audit/chain_after_kan.sh，等 R2-KAN 寫出 result.json → E107 → R2-REG-LONG seed 42。
- 現況錨點：R2-KAN batch 8 @384 convnext_small 佔 5,065 MiB / 8,188 MiB。

## 推論
- 助理在提案時給過一個「估計（非實測）」：activation 隨像素×batch 線性成長，768 是 384 的 4 倍像素，batch 2 + accum 16 可維持相近的 activation 記憶體。原始紀錄明寫這是估計、要等實測確認，而實測從未完成。
- 列出的高解析度路線（依現況排序）：梯度檢查點 + batch 1～2 + 累積；全圖低解析 + 病灶高解析兩路輸入（受 G-DET 閘門阻擋）；切片 + MIL；漸進式解析度。只在推論時提高解析度不可行（尺度錯配）。
- E117 把「高解析度」列入「刻意不做」的項目（時間不夠，寫進限制）。
- 後來 E130（2026-11-13）另寫腳本實測 batch 8／16／32 在現行解析度的峰值顯存，那是不同的問題，不是 E107 的重跑。
