# E40　這個專題沒有封存測試集

- 日期：2026-11-04
- 狀態：完成（事實查核）；三個處置選項交由使用者決定。後來以「排除官方測試集的 manifest」另建保留資料（E120、E123）
- 相關：ADR 0007（可推翻條件第一條因此改寫）、CONTEXT.md 第 3 節；影響 E41、E44、E46、E47、E50 的 val_assess 讀取紀律；後續 E120、E123

## 目的
助理原本想為 ADR 0007（集成是槓桿）事先寫好「請人核准使用封存測試集」的申請並鎖定預測。寫之前先去查那個集合有多大，結果發現它不存在。這份記錄事實、對既有結論的影響，以及可選的處置。

## 做法
- 檢查 `模型改進/data/cp005_manifest.csv` 的 `split` 欄。
- 檢查 `scripts/prepare_split.py` 處理哪些切分、`sealed_test_used` 怎麼寫。
- 對照 `CONTEXT.md` 第 3 節與 `reports/cp005_split.json` 的 `caveat`。
- 盤點 2026-11-04 當天有哪些分析讀過 val_assess。

## 結果
manifest 的 split 只有三個值：

| split | 張數 |
|---|---|
| train | 64,780 |
| val_select | 12,102 |
| val_assess | 9,652 |
| （沒有第四個） | — |

- `prepare_split.py` 第 76、84 行只處理這三個切分，第 85 行把 `'sealed_test_used': False` 寫死在輸出裡。
- `CONTEXT.md` 第 3 節「封存測試集」那一列的張數本來就是「—」。
- `cp005_split.json` 的 caveat 說明 val_assess 的保留性只對 CP-005 成立。

當天讀過 val_assess 並報數字的分析：

| 分析 | 讀 val_assess 做什麼 |
|---|---|
| e36 | 15 個組合器的成績 |
| e36b | 511 個子集中每個大小的最佳子集＋6 個 bootstrap |
| e36c | 36 個配對＋9 個留一＋3 個 bootstrap |
| e37 | 2 個 arm × 4 種校準 |
| e38 | 9 個覆蓋率 × 共錯拆解 |
| e39 | 52 個點的成本–效益＋17 個覆蓋率 |

## 推論
- `sealed_test_used: false` 是協定標記（宣告沒有消耗任何封存保留資料），不是「有一個集合而我們沒碰」。這個宣告一直為真，因為沒有東西可以碰。
- ADR 0007 的第一條可推翻條件「封存測試集上集成沒有贏」寫錯了，同日修正；狀態改為「等一個真正沒被看過的集合確認」。
- val_assess 從未參與任何選擇，但一天內被看過數百個數字，哪些結果值得寫、哪個框架值得強調是看過 val_assess 之後決定的。這是分岔路徑問題，不是資料洩漏，但一樣會讓效果量偏樂觀。
- 因此 ADR 0007 應以完全不需要選擇的「九個等權平均」（+3.49pp，CI [+1.12, +5.66]）為代表，而不是 e36b 掃出來的最佳子集（val_select → val_assess 落差 +2.1 到 +3.5pp）。
- 三個選項，都要人決定：
  - 甲：從 train 切一塊當封存測試集——會改 `manifest_sha256`，既有 17 個 run 失去可比性，不建議。
  - 乙：外部資料集（Fitzpatrick17k／DDI）做分布外驗證——不動 manifest，建議這個。
  - 丙：接受 val_assess，但把使用史寫清楚，主張以不需選擇的組合器為準。
- 之後的分析（E41、E43）刻意做到 val_assess 讀取 0 次，其餘在 JSON 裡記錄讀取次數。
- 後來的發展（執行紀錄 2026-11-12）：使用者要求排除 ISIC 官方測試集，E120 建立排除 ISIC 2018 Task 3 測試集的 manifest，E123 再擴大為排除 ISIC 各屆挑戰賽測試集的 manifest，後續訓練改用該版本。

## 限制
- 這份只確認了切分的存在與否，沒有量化分岔路徑造成的偏差有多大（報告明說無法量化）。
- 讀取次數是當天的盤點，之前各天對 val_assess 的使用沒有逐一計數。
